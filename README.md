# Webカメラのフェイストラッキングによる立体視デモシステム

## 概要
Webカメラを用いてユーザーの顔をトラッキングし、モニターの奥に空間があるように錯覚させる立体視（Portalgraph風）システムです。
Python側で取得した目の位置をUDP通信でUnityへ送信し、モニターを「窓」とみなした投影（Off-Axis Projection）でリアルタイムに描画することで、没入感の高い疑似3D体験を実現しました。

## 動画[https://youtu.be/KINKttTQQCA]

## システム構成
- **顔認識・データ送信**: Python (OpenCV + MediaPipe Face Mesh)
- **3D環境・描画**: Unity (C# / URP)
- **通信プロトコル**: UDPソケット通信 (ローカルネットワーク)

## 主要な機能
- **目の位置の3次元推定**: MediaPipe の虹彩ランドマークから両目の中点を求め、瞳孔間距離とピンホールカメラモデルでWebカメラからの位置（メートル）を計算します。顔を左右に向けても距離が暴れないよう、ランドマークの奥行きも含めて目の間隔を測っています。
- **焦点距離のキャリブレーション**: 決まった距離（50cm）に座って C キーを押すだけで、Webカメラの焦点距離を逆算して保存します。結果を水平画角に換算し、カメラとしてありえない値（40〜95°の範囲外）なら警告を出します。焦点距離は距離 z の推定だけに影響し、小さすぎる（画角が広すぎる）と目が画面に近すぎる位置から描画されて、箱やキャラが奥へ引き伸ばされて見えます。
- **Off-Axis Projection**: 現実のモニターの実寸と目の位置から、目→モニター四隅を通る歪んだ視錐台を毎フレーム計算し、モニターの向こうに空間があるように描画します。
- **前後移動のモード切替**: 本物の窓と同じ見え方の `Window`（標準）と、画角を固定してカメラを前後に動かす `Dolly` を切り替えられます。モニターの枠と背景の境目がずれないのは `Window` だけです。`Depth Gain` で前後の動きへの反応の強さを変えられます（1 = 現実どおり）。
- **低遅延の受信と平滑化**: UDPを別スレッドで受信し、One Euro Filter で「静止時のブレ」と「動いたときの遅延」を両立させています。
- **動きの予測**: カメラは約30fpsですが、受信した位置と速度から「描画する瞬間の位置」を予測し、視点を描画のたびに（60fpsで）動かします。撮影から描画までの経過時間ぶん先を読むので、処理と待ち時間による遅れも打ち消されます。
- **パフォーマンス計測**: fps と遅延の内訳を、トラッカーのプレビュー画面と Unity の画面左上に表示します（下記「パフォーマンス計測」）。
- **ワールド座標グリッドシェーダー**: 壁のScaleを変えてもマス目の大きさが一定で、壁同士の線が角でつながる背景用シェーダー（`Assets/Grid/WorldGrid.shader`）。

## 環境構築

### Python側のセットアップ
仮想環境を作成し、必要なパッケージをインストールして実行準備を行います。

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

### 実行
1. `python tracker.py` を起動します。
2. 初回のみ、Webカメラから50cmの位置に座り、プレビュー画面で **C** キーを押してキャリブレーションします（`calib.json` に保存されます）。
3. Unity側を再生します（ビルドした場合は exe を起動し、Esc で終了）。

### Unity側のセットアップ
Main Camera に `UDPReceiver` と `OffAxisCamera` をアタッチし、インスペクターで以下を設定します。単位はすべてメートルです。
- **Screen Width / Height**: モニターの表示部分の実寸（例: 27インチ16:9 → 0.597 / 0.336）
- **Webcam Offset**: モニター中心から見たWebカメラの位置（上辺中央なら y ≈ 0.18）
- **World Scale**: 現実1mを何Unity単位にするか（大きいほどシーンがミニチュアに見える）
- **Screen**: モニター面の位置。空のオブジェクトを置き、青矢印(Z+)をシーンの奥へ向ける（未設定ならカメラの初期位置）
- **Depth Mode / Depth Gain**: `Window` では目からモニターまでの距離をそのまま投影に使います。`Depth Gain` は前後の動きの倍率で、基準の距離（`Depth Gain Center`、0.6m）からのずれに掛かります。1 以外では距離による見え方が現実とずれ、1 より大きいと奥行きが引き伸ばされ、小さいと距離による変化が控えめになります（基準の距離では 1 と同じ見え方）。

`UDPReceiver` の主な調整項目:
- **Min Cutoff / Min Cutoff Z / Beta**: One Euro Filter の強さ（ブレが気になれば Min Cutoff を下げる、遅れが気になれば Beta を上げる）
- **Prediction**: 動きの予測のオン/オフ
- **Prediction Lead**: カメラ内部・モニター表示など、ソフトで測れない遅延のぶん追加で先読みする時間（秒、目安 0〜0.05）
- **Max Prediction / Velocity Cutoff**: 先読み時間の上限と、速度の推定のなめらかさ

### 現在の設定値（同梱シーン）
| 項目 | 値 | 備考 |
|---|---|---|
| Screen Width / Height | 0.597 / 0.336 m | 27インチ 16:9 |
| World Scale | 4 | 現実1m = 4 Unity単位 |
| Webcam Offset | (0, 0.18, 0) m | モニター上辺中央 |
| Depth Mode / Depth Gain | Window / 0.7 | 奥行きの感じ方が強すぎたため、前後の反応を控えめにしている |

## 動きの予測の仕組み
カメラは約30fpsなので、受信した位置をそのまま使うと、60fpsの描画のうち半分のフレームでは視点が動きません。そこで次のように、描画のたびに現在の位置を予測しています。

```
受信スレッド（約30回/秒）:
  撮影時刻 t = 受信時刻 − proc_ms           ← トラッカー側の処理時間を引く
  速度 v     = (位置 − 前回の位置) / dt を軽くなめらかにしたもの
メインスレッド（描画のたび）:
  先読み時間 h = clamp(現在時刻 − t + Prediction Lead, 0, Max Prediction)
  描画に使う位置 = 位置 + v × h
```

- 補間（1つ前と最新の位置の間をつなぐ）ではなく予測（外挿）にしています。補間はカメラ1フレーム分（約33ms）遅延が増えますが、予測は撮影から描画までの経過時間の分だけ遅延を打ち消せます。
- 毎フレームの計算は掛け算と足し算だけで、重い処理（フィルタ・速度の推定）は受信スレッドで済ませています。
- 0.25秒以上受信が途切れた後は速度を 0 に戻し、先読みには上限を設けて、顔を見失ったときに視点が動き続けないようにしています。

**合成データによる検証**（30fps の合成データ：左右±10cm・0.5Hz で動く頭、ノイズ1mm、処理時間7ms を UDP で送り、60fps で読み出した位置をその瞬間の正解と比較）
| | 予測なし | 予測あり（lead 0） | 予測あり（lead 30ms） |
|---|---|---|---|
| 視点が動かなかったフレームの割合 | 50% | 0% | 0% |
| 位置の誤差（x、RMS） | 16.9 mm | 10.9 mm | 6.6 mm |
| 静止時の1フレームあたりの揺れ（x） | 0.07 mm | 0.11 mm | 0.12 mm |

残る誤差の大半は One Euro Filter の遅れによるものです。この検証にはカメラ内部の遅延を含めていないため、実機での `Prediction Lead` の最適値は見え方で調整しています。

## パフォーマンス計測
### トラッカー（プレビュー画面の黄色い文字・コンソール）
1秒ごとに次の値を表示します（`tracker.py` の `PRINT_STATS` でコンソール出力を切り替え）。
| 表示 | 意味 |
|---|---|
| fps | トラッカーが1秒間に処理したフレーム数 |
| detect | 顔を検出できたフレームの割合 |
| read | 次のフレームを待った時間（ずっと0ms近いなら、処理がカメラより遅くフレームが溜まっている） |
| infer | MediaPipe の推論時間（平均/最大） |
| proc | フレーム取得から UDP 送信までの時間（平均/最大） |

### Unity（画面左上、F1 で表示切り替え）
`PerfOverlay` が再生時に自動で追加されます（シーンの編集は不要）。
| 表示 | 意味 |
|---|---|
| Eye (cm) | 目の位置（Webカメラ基準）。z をメジャーの値と比べるとキャリブレーションのずれが分かる |
| Unity fps / frame | 描画の fps と 1 フレームの時間 |
| Tracker pkt/s / interval / lost | 受信数/秒（≒トラッカーの fps）、受信間隔、パケットロス数 |
| Python proc | トラッカー側の処理時間 |
| Data age | 受信したデータが描画に使われるまでの経過時間 |
| Frame | 描画 1 フレーム分 |
| Total (SW) | ソフトで測れる遅延の合計（カメラ内部・モニター表示は含まない） |
| Prediction | 予測で先読みしている時間 |

UDP で送るデータは `x,y,z,proc_ms,seq`（目の位置[m]、処理時間[ms]、通し番号）です。

### 計測結果（Windows 11 / Anker PowerConf C200 / 1280×720）
**予測なし**（エディタ2回・ビルド2回の計測から、一時的な詰まりがあった1回を除く）
| | 値 |
|---|---|
| Unity 描画 | 60fps（フレーム最大 16.7〜29.1ms） |
| トラッキング | 約30Hz（受信間隔 平均約33.5ms / 最大約54〜63ms、パケットロス 0） |
| Python proc | 平均 6.8〜7.5ms / 最大 8.7〜11.1ms |
| Data age | 平均 16.5〜18.4ms（受信間隔の約半分） / 最大 46〜54ms |
| ソフトで測れる遅延の合計 | 約 41ms（Python 7ms + Data age 17ms + 描画1フレーム 17ms） |

**予測あり**（エディタ）
| | Prediction Lead 0 | Prediction Lead 10ms |
|---|---|---|
| Unity 描画 | 60fps（フレーム最大 16.7ms） | 60fps（フレーム最大 16.8ms） |
| トラッキング | 30.2Hz（間隔 33.2 / 最大 45.1ms） | 29.7Hz（間隔 33.6 / 最大 53.4ms） |
| Python proc | 7.2 / 10.7ms | 7.9 / 18.3ms |
| Data age | 16.5 / 47.3ms | 18.5 / 49.6ms |
| 先読み時間（Prediction） | 22.8ms | 36.2ms |

- 描画は60fpsのままで、予測の計算による負荷は見られません。
- 先読み時間は計算どおりです（lead 0：7.2 + 16.5 ≈ 22.8ms、lead 10ms：7.9 + 18.5 + 10 ≈ 36.2ms）。Python proc と Data age の分（約24〜26ms）は予測で打ち消され、残るのは描画1フレーム分（16.7ms）です。オーバーレイの `Total (SW)` は、予測で打ち消した分を引く前の値です。

**分析**
- トラッキングのボトルネックはカメラの fps です（60fps を要求しても約30fps で動作）。MediaPipe の推論は約7ms で、ボトルネックではありません。
- エディタとビルドの差はほとんどありません。
- カメラ内部（露光〜転送、30fps で 1〜2 フレーム）とモニター表示はソフトでは測れません。予測を入れる前の全体の遅延は、これらを含めて約 85〜130ms と推定しています（未実測）。全体の遅延は、スマホのスロー撮影（240fps）で頭と画面を同時に撮り、頭が止まってから画面が止まるまでのコマ数 × 約4.2ms で測れます。
