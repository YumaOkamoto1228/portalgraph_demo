# Webカメラのフェイストラッキングによる立体視デモシステム

## 概要
Webカメラを用いてユーザーの顔をトラッキングし、モニターの奥に空間があるように錯覚させる立体視（Portalgraph風）システムです。
Python側で取得した目の位置をUDP通信でUnityへ送信し、モニターを「窓」とみなした投影（Off-Axis Projection）でリアルタイムに描画することで、没入感の高い疑似3D体験を実現しました。

## 動画[https://youtu.be/KINKttTQQCA]

## システム構成
- **顔認識・データ送信**: Python (OpenCV + MediaPipe Face Mesh)
- **3D環境・描画**: Unity (C# / URP)
- **通信プロトコル**: UDPソケット通信 (ローカルネットワーク)

## 主要な機能
- **目の位置の3次元推定**: MediaPipe の虹彩ランドマークから両目の中点を求め、瞳孔間距離とピンホールカメラモデルでWebカメラからの位置（メートル）を計算します。顔を左右に向けても距離が暴れないよう、ランドマークの奥行きも含めて目の間隔を測っています。
- **焦点距離のキャリブレーション**: 決まった距離（50cm）に座って C キーを押すだけで、Webカメラの焦点距離を逆算して保存します。結果を水平画角に換算し、カメラとしてありえない値（40〜95°の範囲外）なら警告を出します。
- **Off-Axis Projection**: 現実のモニターの実寸と目の位置から、目→モニター四隅を通る歪んだ視錐台を毎フレーム計算し、モニターの向こうに空間があるように描画します。
- **前後移動のモード切替**: 本物の窓と同じ見え方の `Window`（標準）と、画角を固定してカメラを前後に動かす `Dolly` を切り替えられます。モニターの枠と背景の境目がずれないのは `Window` だけです。
- **低遅延の受信と平滑化**: UDPを別スレッドで受信し、One Euro Filter で「静止時のブレ」と「動いたときの遅延」を両立させています。
- **動きの予測**: カメラは約30fpsですが、受信した位置と速度から「描画する瞬間の位置」を予測し、視点を描画のたびに（60fpsで）動かします。撮影から描画までの経過時間ぶん先を読むので、処理と待ち時間による遅れも打ち消されます。
- **パフォーマンス計測**: fps と遅延の内訳を、トラッカーのプレビュー画面と Unity の画面左上に表示します（下記「パフォーマンス計測」）。
- **ワールド座標グリッドシェーダー**: 壁のScaleを変えてもマス目の大きさが一定で、壁同士の線が角でつながる背景用シェーダー（`Assets/Grid/WorldGrid.shader`）。

## 環境構築

### Python側のセットアップ
仮想環境を作成し、必要なパッケージをインストールして実行準備を行います。

```bash
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

### 実行
1. `python tracker.py` を起動します。
2. 初回のみ、Webカメラから50cmの位置に座り、プレビュー画面で **C** キーを押してキャリブレーションします（`calib.json` に保存されます）。
3. Unity側を再生します（ビルドした場合は exe を起動し、Esc で終了）。

### Unity側のセットアップ
Main Camera に `UDPReceiver` と `OffAxisCamera` をアタッチし、インスペクターで以下を設定します。単位はすべてメートルです。
- **Screen Width / Height**: モニターの表示部分の実寸（例: 27インチ16:9 → 0.597 / 0.336）
- **Webcam Offset**: モニター中心から見たWebカメラの位置（上辺中央なら y ≈ 0.18）
- **World Scale**: 現実1mを何Unity単位にするか（大きいほどシーンがミニチュアに見える）
- **Screen**: モニター面の位置。空のオブジェクトを置き、青矢印(Z+)をシーンの奥へ向ける（未設定ならカメラの初期位置）

`UDPReceiver` の主な調整項目:
- **Min Cutoff / Min Cutoff Z / Beta**: One Euro Filter の強さ（ブレが気になれば Min Cutoff を下げる、遅れが気になれば Beta を上げる）
- **Prediction**: 動きの予測のオン/オフ
- **Prediction Lead**: カメラ内部・モニター表示など、ソフトで測れない遅延のぶん追加で先読みする時間（秒、目安 0〜0.05）
- **Max Prediction / Velocity Cutoff**: 先読み時間の上限と、速度の推定のなめらかさ

## パフォーマンス計測
### トラッカー（プレビュー画面の黄色い文字・コンソール）
1秒ごとに次の値を表示します（`tracker.py` の `PRINT_STATS` でコンソール出力を切り替え）。
| 表示 | 意味 |
|---|---|
| fps | トラッカーが1秒間に処理したフレーム数 |
| detect | 顔を検出できたフレームの割合 |
| read | 次のフレームを待った時間（ずっと0ms近いなら、処理がカメラより遅くフレームが溜まっている） |
| infer | MediaPipe の推論時間（平均/最大） |
| proc | フレーム取得から UDP 送信までの時間（平均/最大） |

### Unity（画面左上、F1 で表示切り替え）
`PerfOverlay` が再生時に自動で追加されます（シーンの編集は不要）。
| 表示 | 意味 |
|---|---|
| Eye (cm) | 目の位置（Webカメラ基準）。z をメジャーの値と比べるとキャリブレーションのずれが分かる |
| Unity fps / frame | 描画の fps と 1 フレームの時間 |
| Tracker pkt/s / interval / lost | 受信数/秒（≒トラッカーの fps）、受信間隔、パケットロス数 |
| Python proc | トラッカー側の処理時間 |
| Data age | 受信したデータが描画に使われるまでの経過時間 |
| Frame | 描画 1 フレーム分 |
| Total (SW) | ソフトで測れる遅延の合計（カメラ内部・モニター表示は含まない） |
| Prediction | 予測で先読みしている時間 |

UDP で送るデータは `x,y,z,proc_ms,seq`（目の位置[m]、処理時間[ms]、通し番号）です。

### 計測例（Windows 11 / Anker PowerConf C200 / 1280×720）
| | 値 |
|---|---|
| Unity 描画 | 60fps |
| トラッキング | 約30Hz（カメラが約30fpsで動作） |
| Python 処理時間 | 約6〜8ms（最大約11ms） |
| Data age | 平均約17ms（受信間隔約33msの半分） |
| ソフトで測れる遅延の合計 | 約41ms（予測なしの場合） |

トラッキングのボトルネックはカメラの fps で、推論はボトルネックではありません。カメラ内部とモニター表示を含む全体の遅延は、スマホのスロー撮影（240fps）で頭と画面を同時に撮って測ります。
